# Day 2. 런북 RAG와 평가셋

[← 전체 미션 맵](../README.md)  ·  [← Day 1](../day01/README.md)  ·  [Day 3 →](../day03/README.md)

> 운영 런북을 검색해 근거와 함께 답하고, 그 답의 품질을 스스로 재는 평가셋까지 만듭니다.

## 학습 목표

- 메타데이터를 청킹 전에 붙여야 상속된다는 사실을 직접 확인합니다.
- 검색 결과를 프롬프트에 실제로 주입하고, 어느 문서를 근거로 썼는지 함께 돌려줍니다.
- 답이 틀렸을 때 검색 단계부터 의심하는 법을 익힙니다. (심화)
- 이 과정 전체를 관통할 `eval_set.json`을 여기서 시작합니다.

## 왜 중요한가

오늘 만드는 산출물 두 개는 Day7까지 계속 씁니다.

| 산출물 | 어디서 쓰이나 |
|---|---|
| `eval_set.json` | Day3·4·5·6에서 문항이 누적되고, Day7에서 전체를 실행해 유형별 통과율을 냅니다 |
| 인덱싱 파이프라인 | Day6 Supervisor의 `runbook_agent` 도구가 됩니다 |

## 기초 파트 (7점)

### 구현할 것

```python
build_chunks(doc_paths)             # 문서 경로 목록 -> Document 리스트
build_retriever(vectorstore)        # 벡터저장소 -> retriever
build_rag_chain(retriever, llm=None)  # 질문 -> {"answer": str, "sources": [...]}
```

### 요구사항

1. `build_chunks`: 모든 청크의 `metadata`에 세 키가 있어야 합니다.

   | 키 | 값 |
   |---|---|
   | `source` | 원본 파일명 |
   | `department` | 담당 조직 |
   | `updated_at` | 최종 수정일 (`YYYY-MM-DD`) |

   > **메타데이터는 청킹 *전에* 붙여야 합니다.** 순서를 틀리면 상속이 안 되는데, 오류도 나지 않아서 한참 뒤에야 알아챕니다.
   >
   > 분할에는 `RecursiveCharacterTextSplitter`나 `MarkdownHeaderTextSplitter`를 쓰세요.
   >
   > 실습 문서는 740~921자입니다. **`chunk_size`는 800 이하로 잡으세요.**
   > 그보다 크면 통째로 한 청크가 되어 버리는 문서가 생깁니다.

2. `build_retriever`: `vectorstore.as_retriever(...)`로 만들고 `k`를 명시하세요.

3. `build_rag_chain`: 질문 문자열을 받아 아래 형태를 반환합니다.

   ```python
   {"answer": "연차는 최대 5일까지 이월됩니다.", "sources": ["leave_policy.md"]}
   ```

   `sources`에는 실제로 검색된 문서에서 뽑은 값을 넣습니다. 지어낸 파일명이 들어가면 안 됩니다.

4. `eval_set.json` (저장소 루트): 5문항 이상을 쓰되, 아래 세 유형을 모두 포함합니다.

   ```json
   [
     {"id": "d2-01", "question": "연차는 며칠까지 이월되나요?",
      "type": "fact", "expected_source": "leave_policy.md"},
     {"id": "d2-02", "question": "남은 휴가를 내년에 쓸 수 있나요?",
      "type": "paraphrase", "expected_source": "leave_policy.md"},
     {"id": "d2-03", "question": "사내 헬스장 운영 시간은?",
      "type": "no_answer", "expected_source": null}
   ]
   ```

   | 유형 | 뜻 |
   |---|---|
   | `fact` | 문서에 그대로 적힌 것을 묻습니다 |
   | `paraphrase` | 같은 내용을 다른 말로 묻습니다 (검색이 진짜 되는지 확인) |
   | `no_answer` | 문서에 없는 것을 묻습니다. 모른다고 답해야 정답입니다 |

   > id는 `d{Day번호}-{일련번호}` 형식으로 씁니다 (예: `d2-01`).
   > Day3 이후 추가분은 `d3-`, `d4-` …로 이어 붙이세요. **id는 저장소 전체에서 중복되면 안 됩니다.**

### 채점 기준 (기초 7점)

| 배점 | 항목 | 무엇을 보는가 |
|---|---|---|
| 2점 | **메타데이터 상속** | 모든 청크에 세 키가 존재. 청킹 전에 붙였는지를 봅니다 |
| 1점 | **청킹 전략** | 청크 수가 합리적 범위이고 원문이 보존됨. 단순 고정 길이 자르기가 아님 |
| 2점 | **컨텍스트 주입** | 검색된 문서 본문이 모델에게 보낸 프롬프트에 실제로 들어 있음 |
| 1점 | **출처 반환** | `sources`가 실제 검색 결과와 일치. 지어낸 값이 아님 |
| 1점 | **확장 검사 게이트** | 10개 중 8개 이상 |

## 심화 파트 (3점)

### 왜 필요한가

RAG가 틀린 답을 내놓으면 프롬프트부터 손대게 됩니다. 정작 검색이 정답 청크를 못 가져왔다면 모델을 바꿔도 소용없습니다.
답을 만들기 전에 검색 결과부터 보고, 쓸만하지 않으면 모른다고 답하세요.

### 구현할 것

```python
assess_retrieval(docs, question) -> dict
```

그리고 `build_rag_chain`이 이 판정을 거쳐 동작하도록 연결합니다.

### 요구사항

1. 검색 품질 판정: `assess_retrieval`은 **LLM을 호출하지 않고** 검색 결과가 쓸만한지 판정합니다.

   ```python
   {"usable": True, "reason": "질의어 3개 중 2개가 본문에 등장", "matched": 2}
   ```

   판정 근거는 자유롭게 잡으세요. 조건은 결정적이어야 한다는 것 하나입니다. 같은 입력에는 항상 같은 출력이 나와야 합니다.
   > 예: 질문에서 핵심어를 뽑아 문서 본문에 몇 개나 등장하는지 세기, 문서 개수·길이 확인 등

2. 검색 결과가 없거나 쓸모없으면 거절: `usable`이 `False`면 모델에게 묻지 않고 바로 거절 응답을 만듭니다.

   ```python
   {"answer": "제공된 문서에서 답을 찾을 수 없습니다.", "sources": []}
   ```

   거절 응답에는 `찾을 수 없` 문구가 들어가야 합니다. 그리고 `sources`는 빈 목록으로 둡니다.

3. 연결: 문서와 무관한 질문을 넣었을 때 체인이 사실을 지어내지 않아야 합니다.

### 채점 기준 (심화 3점)

| 배점 | 항목 | 무엇을 보는가 |
|---|---|---|
| 1점 | **판정의 결정성** | 관련 문서 / 무관 문서 / 빈 목록에서 각각 다르게 판정. 상수 반환이면 실패 |
| 1점 | **거절 경로** | 검색 결과가 비었을 때 모델을 호출하지 않고 거절. `sources`가 빈 목록 |
| 1점 | **파이프라인 연결** | 무관한 질문에서 모델이 그럴듯한 답을 줘도 체인이 그 답을 거절로 바꿈 |
