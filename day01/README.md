# Day 1. 운영 알람 트리아지 체인

[← 전체 미션 맵](../README.md)  ·  [Day 2 →](../day02/README.md)

> 모니터링 알람을 구조화된 분류 결과로 바꾸고, 담당팀에 보낼 안내 초안까지 한 번에 뽑습니다.

## 학습 목표

- LLM에게 형식을 강제하는 방법을 익힙니다. 프롬프트에 "JSON으로 답해"라고 적어 두면 모델이 지킬 때도 있고 안 지킬 때도 있습니다. 스키마와 파서로 강제하면 어긴 출력이 파서에서 걸립니다.
- LCEL로 부품(프롬프트, 모델, 파서)을 조립하고 `RunnableParallel`로 두 갈래를 한 번에 실행합니다.
- LLM의 판단 위에 결정적 규칙을 얹는 하이브리드 구조를 만들어 봅니다. (심화)

## 시나리오

운영 중인 서비스에서 알람이 옵니다.

```json
{
  "alert_id": "ALT-2026-0811-0042",
  "service": "payment-api",
  "raised_at": "2026-08-11T03:14:22+09:00",
  "message": "HTTP 5xx ratio 12.4% over 5m (threshold 1%)",
  "region": "ap-northeast-2"
}
```

당직자는 이 알람을 보고 얼마나 급한지, 어느 팀이 볼지, 무엇부터 확인할지를 정합니다. 이 판단을 체인으로 만듭니다.

---

## 기초 파트 (7점)

### 무엇을 만드나

알람 하나를 넣으면 두 결과를 동시에 돌려주는 체인입니다.

| 갈래 | 반환 | 용도 |
|---|---|---|
| `triage` | 구조화된 dict | 티켓 시스템에 그대로 적재 |
| `notice` | 자연어 문장 | 담당팀 채널에 붙여넣을 안내 초안 |

### 구현할 것

`practice/starter/submission.py`의 TODO를 채웁니다. **이름과 시그니처는 바꾸지 마세요.** 채점기가 이 이름으로 함수를 찾습니다.

```python
TRIAGE_SCHEMA                      # 분류 결과 Pydantic 스키마
build_triage_chain(llm=None)       # 알람 -> 구조화 dict
build_notice_chain(llm=None)       # 알람 -> 안내 초안 문자열
build_full_chain(llm=None)         # 위 둘을 병렬로 묶어 dict 반환
```

### 요구사항

1. `TRIAGE_SCHEMA`: `BaseModel`을 상속하고 필드 4개 이상을 둡니다. 모든 필드에 `description`을 답니다.
   모델이 보는 것은 필드 이름과 이 설명문뿐이라, 설명이 비어 있으면 그 필드가 무엇인지 모릅니다.
   - `severity`는 `Literal` 또는 `Enum`으로 정해진 값 중 하나만 받게 하세요.
2. `build_triage_chain`: `prompt | llm | parser` 형태로 조립하고, 파서의 `format_instructions`를 프롬프트에 실제로 주입합니다.
3. `build_notice_chain`: system 메시지로 역할을 지정하세요. 교안 예시 문구는 지우고 본인 조직의 말투와 맥락으로 다시 씁니다.
4. `build_full_chain`: `RunnableParallel`로 두 체인을 묶어 `{"triage": ..., "notice": ...}` 형태로 반환합니다.

### 채점 기준 (기초 7점)

| 배점 | 항목 | 무엇을 보는가 |
|---|---|---|
| 2점 | **스키마 계약** | `TRIAGE_SCHEMA`가 `BaseModel` 서브클래스이고 필드 4개 이상. 모든 필드에 `description`이 있고, `severity`가 열거형으로 제한됨 |
| 2점 | **병렬 조립** | `build_full_chain` 결과가 `triage`·`notice` 두 키를 가진 dict이고, 두 갈래가 각각 채워짐 |
| 1점 | **형식 지침 주입** | 분류 체인이 모델에게 보낸 프롬프트에 파서의 `format_instructions` 내용이 실제로 들어 있음 |
| 1점 | **역할 지정** | 안내 체인에 system 메시지가 있고 30자 이상이며 starter 기본 문구와 다름 |
| 1점 | **확장 검사 게이트** | 아래 10개 중 8개 이상 통과 |

확장 검사 10개는 알람 모양이 흔들려도 파이프라인이 버티는지 봅니다.

`message`가 빈 문자열 / `service` 키 누락 / 본문이 4000자로 긴 알람 / 한글·영문 혼재 / 특수문자와 이모지 / `raised_at`이 잘못된 형식 / 숫자만 있는 메시지 / 중첩 dict가 섞인 알람 / 알람 2건 연속 처리 / 같은 알람 재처리 시 동일 구조 반환

## 심화 파트 (3점)

> 기초를 통과했다면 여기까지 해 보세요. 심화를 못 해도 과제는 통과합니다.
> 대신 통과하면 대시보드에 심화 달성으로 기록되고, Mini PJT에서 이 코드를 그대로 씁니다.

### 왜 필요한가

LLM은 형식을 잘 지키다가도 어느 순간 깨뜨립니다. 게다가 `payment-api`가 죽었다면 모델이 뭐라고 분류했든 최우선입니다.
이런 판단까지 모델에게 맡길 이유는 없습니다. LLM이 매긴 등급을 받아 온 다음, 정해 둔 규칙으로 한 번 더 덮어쓰세요.

### 구현할 것

```python
apply_severity_rules(triage: dict, alert: dict) -> dict
```

그리고 `build_full_chain`이 이 함수를 파이프라인 안에서 호출하도록 연결합니다.

### 요구사항

1. 깨진 출력 복구: 모델이 JSON이 아닌 것을 뱉어도 `build_full_chain`은 예외를 던지지 않고 dict를 반환해야 합니다.
   복구된 결과에는 그 사실을 알 수 있는 표시를 남기세요 (예: `severity`를 가장 높은 값으로 두거나 `parse_failed` 같은 표시).
   > 힌트: `try/except`로 감싸 기본값을 돌려줘도 되고, `OutputFixingParser`나 재시도를 붙여도 됩니다. 방법은 자유입니다.

2. 결정적 규칙 오버라이드: `apply_severity_rules`는 LLM을 호출하지 않고 다음 규칙을 적용합니다.

   | 조건 | 처리 |
   |---|---|
   | `service`가 중요 서비스 목록에 있음 | severity를 최소 `P2`로 올림 (이미 더 높으면 유지) |
   | `message`에 `5xx` 또는 `outage`가 포함 | severity를 최소 `P1`로 올림 |
   | 위 둘 다 해당 | 더 높은 쪽을 적용 |
   | 아무 조건도 해당 없음 | 모델 판단을 그대로 둠 |

   중요 서비스 목록은 모듈 상수로 두고, 최소 3개 이상 넣습니다.
   규칙이 적용됐다면 그 사실을 결과에 남기세요 (예: `rule_applied` 키).

3. 연결: `build_full_chain`의 `triage` 결과가 규칙 적용을 거친 값이어야 합니다.

### 채점 기준 (심화 3점)

| 배점 | 항목 | 무엇을 보는가 |
|---|---|---|
| 1점 | **깨진 출력 복구** | 모델이 `"죄송합니다, 알 수 없습니다"`처럼 JSON이 아닌 응답을 해도 예외 없이 dict 반환. 복구 표시 존재 |
| 1점 | **규칙의 결정성** | `apply_severity_rules`를 LLM 없이 직접 호출했을 때, 4가지 조건 조합에서 규칙표대로 동작. 상수 반환이면 실패 |
| 1점 | **파이프라인 연결** | `build_full_chain` 결과의 `triage`에 규칙 적용 흔적이 남아 있음 |
