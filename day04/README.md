# Day 4. 운영 지원 MCP 서버와 장애 복구

[← 전체 미션 맵](../README.md)  ·  [← Day 3](../day03/README.md)  ·  [Day 5 →](../day05/README.md)

> 사내 운영 데이터를 표준 프로토콜로 노출하고, 외부 호출이 실패해도 답을 만들어 냅니다.

## 학습 목표

- 모델이 도구를 고를 때 보는 것은 이름과 설명, 인자 스키마입니다. 하나라도 비면 엉뚱한 도구를 부릅니다.
- 에러 메시지가 LLM에게 주는 프롬프트로 쓰인다는 것을 확인합니다.
- MCP가 M×N을 M+N으로 바꾸는 원리를 보고, 서버를 직접 만들어 봅니다.
- 장애 종류마다 대응이 어떻게 갈리는지 따져 봅니다. (심화)

---

## 기초 파트 (7점)

### 구현할 것

```python
TOOL_SPECS                                   # MCP로 노출할 도구 명세 3개
TOOLS_IMPL                                   # 이름 -> 실제 함수
get_asset_status(asset_id, fetch=None)       # 재시도 + 대체 경로
get_asset_status_backup(asset_id)            # 대체 조회 경로
```

여기에 더해 `day04/mcp_server.py`에 `fastmcp` 서버를 만들고 위 도구를 노출하세요.

### 요구사항

1. 도구 3개: `search_runbook`, `get_service_owner`, `query_recent_incidents`

   `TOOL_SPECS`의 각 항목은 아래 형태입니다.

   ```python
   {
     "name": "search_runbook",
     "description": "증상 키워드로 대응 런북을 찾습니다. ...",   # 30자 이상
     "args": {"symptom": "증상 키워드. 예: 5xx, oom, cert"},     # 인자마다 설명
   }
   ```

   `TOOLS_IMPL`은 `{"search_runbook": search_runbook, ...}` 형태이고, 각 함수는 문자열을 반환합니다.
   없는 값을 넣었을 때도 예외를 던지지 말고, 무엇이 잘못됐는지 알려 주는 문자열을 돌려주세요.

2. `get_asset_status(asset_id, fetch=None)`에서 `fetch`는 외부 백엔드를 부르는 함수입니다.
   - `fetch`가 없으면 기본 조회를 씁니다.
   - `fetch`가 실패하면 재시도하고, 그래도 안 되면 `get_asset_status_backup`으로 넘어갑니다.
   - **어떤 경우에도 예외를 밖으로 던지지 않습니다.** 상황을 설명하는 문자열을 대신 반환하세요.
   - 대체 경로로 넘어갔다면 반환 문자열에 `get_asset_status_backup`이라는 이름을 남기세요.
     모델이 그다음에 무엇을 할지 고르려면 이 이름이 필요합니다.

3. 로그에 자격증명을 남기지 않습니다. 키나 토큰 문자열이 반환값이나 로그에 그대로 들어가면 안 됩니다.

4. `eval_set.json`에 문항을 추가합니다 (저장소 루트). `tool_recovery` 유형으로 2문항 이상 쓰세요.
   도구가 실패했을 때 복구했는지를 묻는 질문입니다. id는 `d4-01` 형식으로 이어 붙입니다.

### 채점 기준 (기초 7점)

| 배점 | 항목 | 무엇을 보는가 |
|---|---|---|

| 2점 | **호출 동작** | 정상 인자는 기대 값을, 없는 값은 예외 대신 안내 문자열을 반환 |

## 심화 파트 (3점)

### 왜 필요한가

실패하면 일단 재시도부터 거는 코드가 많습니다. 스키마가 틀린 응답은 백 번 재시도해도 틀린 채로 돌아오면서 시간과 API 예산만 씁니다.
재시도를 걸기 전에 어떤 실패인지부터 갈라 보세요.

### 구현할 것

```python
classify_failure(error) -> str    # "retryable" | "backoff" | "fatal"
```

이 분류 결과에 따라 `get_asset_status`의 동작이 갈리도록 연결하세요.

| 분류 | 무엇 | 처리 |
|---|---|---|
| `retryable` | 타임아웃, 일시적 연결 오류 | 짧게 재시도 |
| `backoff` | 요청 한도 초과 (rate limit) | 간격을 늘려 재시도 |
| `fatal` | 스키마 오류, 인증 실패, 없는 자원 | 재시도하지 않고 즉시 대체 경로 |

### 채점 기준 (심화 3점)

| 배점 | 항목 | 무엇을 보는가 |
|---|---|---|
| 1점 | **분류의 결정성** | 6가지 오류 상황에서 표대로 분류. 상수 반환이면 실패 |
| 1점 | **fatal 즉시 폴백** | 스키마 오류에서 재시도 횟수가 1회 이하 |
| 1점 | **retryable은 재시도** | 타임아웃에서는 2회 이상 재시도하고, 총 호출은 상한 이하 |
